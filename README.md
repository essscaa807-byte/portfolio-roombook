# RoomBook — кейс системного анализа: бронирование переговорных комнат

Учебный кейс: полный комплект артефактов системного анализа для внутреннего сервиса бронирования
переговорных комнат — от требований и NFR до OpenAPI-контракта и матрицы трассируемости.

Комплект собран по принципу Docs-as-Code: всё в Markdown/PlantUML/YAML, проверяется скриптами,
а не «на глаз».

## Что показывает этот кейс

| Навык | Где смотреть |
|---|---|
| Формулировка атомарных требований | `srs/srs.md` — 20 требований в 6 доменах |
| Нефункциональные требования с методами проверки | `quality/nfr_catalog.md` — 12 NFR |
| Сценарии использования и критерии приёмки | `srs/srs.md` — UC-01, UC-02 и 26 AC в Given/When/Then |
| Трассируемость | `rtm/rtm.csv` — 20 строк: REQ → источник → компонент → AC → артефакт |
| Моделирование процессов | `processes/*.puml` — BPMN бронирования и Sequence для UC-01 |
| Модель данных | `data/er_roombook.puml`, `data/dictionary.md` |
| API-контракт | `contracts/openapi.yaml` — OpenAPI 3.0.3, 7 эндпоинтов, RFC 7807 |

## Стейкхолдеры

| Стейкхолдер | Интерес | Как учтён |
|---|---|---|
| Сотрудник (EMPLOYEE) | быстро найти и занять свободную комнату | UC-01, `GET /rooms`, `GET /rooms/{id}/slots`, `POST /bookings` |
| Администратор (ADMIN) | управлять справочником и порядком | `POST /admin/rooms`, отмена любой брони |
| Владелец офиса (заказчик) | прозрачная загрузка комнат | `GET /admin/reports/load` (CSV), цель по медиане времени |
| Внешний календарный сервис | получать события бронирования | REQ-INT-001…003, Sequence Diagram |

## Цели (измеримые)

| Цель | Критерий | Где проверяется |
|---|---|---|
| Убрать согласование через чат | 100% броней создаются без ручного согласования | REQ-BOOK-001 |
| Не допускать двойного бронирования | 0 пересечений CONFIRMED-броней по комнате | REQ-BOOK-002, AC-009 |
| Ускорить просмотр слотов | p95 ≤ 300 мс на `GET /rooms` и `/slots` | NFR-PERF-001 |
| Прозрачная загрузка | CSV-отчёт за любой период ≤ 366 дней | REQ-REPORT-001, REQ-REPORT-002 |

## Как читать кейс (порядок)

1. `srs/srs.md` — что строим и почему; здесь же критерии приёмки.
2. `quality/nfr_catalog.md` — каким требованиям качества система должна соответствовать.
3. `processes/booking_process.puml` — как выглядит процесс до кода (или откройте `render/*.svg`).
4. `data/er_roombook.puml` + `data/dictionary.md` — на чём это держится.
5. `contracts/openapi.yaml` — как это выглядит для клиента.
6. `rtm/rtm.csv` — чем всё связано между собой.

## Результат в цифрах

- **20** функциональных требований в доменах AUTH, VIEW, BOOK, ADMIN, INT, REPORT.
- **26** критериев приёмки Given/When/Then, у каждого требования — минимум один.
- **12** нефункциональных требований (PERF, REL, SEC, OBS, DATA), у каждого метод проверки и инструмент.
- **7** эндпоинтов в OpenAPI 3.0.3, 7 уникальных `operationId`, ошибки в формате RFC 7807.
- **20** строк в матрице трассируемости, все REQ покрыты.
- **3** диаграммы PlantUML, отрендерены в SVG.

## Проверки

```bash

python tools/validate-roombook.py

# валидность OpenAPI
python -m openapi_spec_validator contracts/openapi.yaml
# или
npx @redocly/cli lint contracts/openapi.yaml
```

## Границы и ограничения

- Внешний календарь — заглушка: зафиксировано поведение при недоступности (retry ≤ 3), но не протокол
  интеграции.
- Админка комнат в контракте — только создание (`POST /admin/rooms`); редактирование и деактивация
  описаны в SRS как развитие.
- Данные синтетические: `user@example.com`, `Room-1`; совпадения с реальными компаниями случайны.
- Брони создаются сразу в статусе `CONFIRMED` — согласование не входит в MVP.
