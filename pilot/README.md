# Пилот RoomBook: протокол, данные и отчёт

## Статус данных (честно)

В репозитории лежит **симуляция**, а не результаты реального пилота: офиса и пользователей нет.
`pilot/pilot_report.md` начинается с явной пометки об этом. Симуляция нужна для двух вещей:

1. зафиксировать **набор метрик**, которые пилот обязан собирать;
2. дать готовый расчёт, который переиспользуется на реальных данных без изменения логики.

## Состав

| Файл | Что это |
|---|---|
| `simulate_pilot.py` | генератор событий: 12 комнат, 40 сотрудников, 90 дней, seed = 42 |
| `bookings.csv` | успешные брони: комната, время (UTC и МСК), длительность, lead time, статус |
| `events.csv` | все попытки: `CONFIRMED`, `CANCELLED`, `CANCELLED_TOO_LATE`, `REJECTED_CONFLICT` |
| `pilot_report.md` | отчёт: воронка, метрики, загрузка по комнатам, часам и дням недели |

## Как запустить настоящий пилот (1 неделя)

**Шаг 1. Пилотная группа.** 8–12 сотрудников, 3–4 комнаты. Меньше — не будет статистики,
больше — участники начнут обходить систему.

**Шаг 2. Сбор.** Включить на портале запись событий (журнал) в одном формате с `events.csv`.
Если портала ещё нет — 1 неделя ручной фиксации в общей таблице по той же схеме.

**Шаг 3. Минимальный набор метрик** — ровно то, что считает отчёт:

| Метрика | Зачем | Целевое значение (гипотеза) |
|---|---|---|
| Доля отказов из-за пересечения | качество поиска слотов | ≤ 10% |
| Доля поздних отмен | дисциплина бронирования | ≤ 5% |
| Доля броней в день встречи | потребность в «быстром» бронировании | 30–40% |
| Медианная длительность | размер слотов по умолчанию | 30–60 мин |
| Загрузка по комнатам | нужны ли все комнаты | разброс ≤ 3× |
| p95 времени ответа | NFR-PERF-001 | ≤ 300 мс |

**Шаг 4. Exit-критерии пилота.**
Пилот считается успешным, если: ≥ 80% броней созданы без обращения в поддержку; доля конфликтов
≤ 10%; ни одной жалобы на двойное бронирование; p95 ≤ 300 мс.

**Шаг 5. Что делать с результатами.** Отчёт прикладывается к решению о раскатке; расхождения
с гипотезами фиксируются как изменения требований, а не как «пилот не удался».

## Формат данных (контракт для интеграции)

`events.csv`:

| Колонка | Тип | Значение |
|---|---|---|
| `booking_id` | string | `b00001` |
| `employee` | string | `user01@example.com` |
| `room` | string | `Room-1` |
| `start_utc` | ISO-8601 | `2026-09-01T06:30:00+00:00` |
| `end_utc` | ISO-8601 | `2026-09-01T07:00:00+00:00` |
| `status` | enum | `CONFIRMED`, `CANCELLED`, `CANCELLED_TOO_LATE`, `REJECTED_CONFLICT` |

`bookings.csv` дополнительно содержит `capacity`, `start_local`, `end_local`, `duration_min`,
`lead_minutes`.

Такой же набор полей отдаёт журнал портала; если реальная система отдаёт другие имена —
достаточно маппинга в одну функцию, отчёт не меняется.

## Ограничения симуляции

- Нет данных о неявках (no-show): в MVP нет check-in, их физически нечем измерить.
- Нет времени ответа API: это нагрузочный тест, а не пилот.
- Распределение часов задано экспертно (утро и после обеда), а не снято с реального офиса.
- Комнаты и сотрудники вымышлены; названия нейтральные.
