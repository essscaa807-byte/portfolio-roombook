# SRS — RoomBook, сервис бронирования переговорных комнат

Версия: 1.0.0 · Статус: baseline · Дата: 22.11.2026
Формат: гибридный (ISO/IEC/IEEE 29148 + практики Agile-аналитики)

## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Наименование системы | RoomBook — внутренний сервис бронирования переговорных комнат |
| Заказчик | Владелец офиса (представитель бизнеса) |
| Пользователи | Сотрудник (EMPLOYEE), Администратор (ADMIN) |
| Границы MVP | аутентификация, просмотр слотов, создание и отмена брони, админка комнат, интеграция с внешним календарём (заглушка), CSV-отчёт по загрузке |
| Вне MVP | мобильное приложение, SMS-уведомления, интеграция с турникетами |
| Цель | убрать ручное согласование переговорных через чат и почту: сотрудник видит свободные слоты и бронирует сам |

## 2. Назначение и границы

Система автоматизирует подбор и бронирование переговорных комнат внутри одной организации.
Хранение времени — UTC (`timestamptz`), отображение и ввод — Europe/Moscow. Рабочие часы бронирования:
09:00–19:00 по Москве, шаг слотов 30 минут.

Ограничения MVP, принятые как данность:

1. Бронь создаётся сразу в статусе `CONFIRMED` (согласование не требуется).
2. Сотрудник может отменить только свою бронь и не позднее чем за 1 час до начала.
3. Администратор может отменить любую бронь в любое время.
4. Внешний календарь — заглушка: недоступность не блокирует бронирование, события уходят с повторами.

## 3. Глоссарий

| Термин | Определение |
|---|---|
| Слот | интервал 30 минут в рабочих часах комнаты, отображаемый как `free` или `busy` |
| Бронь | резерв комнаты сотрудником на интервал; статус `CONFIRMED` или `CANCELLED` |
| Пересечение | ситуация, когда интервал новой брони пересекается с интервалом существующей `CONFIRMED` брони той же комнаты |
| Ведущий (organizer) | сотрудник, создавший бронь |
| Внешний календарь | внешний сервис, куда публикуются события бронирования (в MVP — заглушка) |
| Идемпотентность | повторный запрос с тем же `Idempotency-Key` не создаёт вторую бронь |

## 4. Функциональные требования

Формулировки атомарные, проверяемые: «Система ДОЛЖНА …».

### 4.1. Аутентификация и доступ (AUTH)

**REQ-AUTH-001.** Система ДОЛЖНА аутентифицировать пользователя по паре email и пароль и выдавать
JWT-токен доступа со сроком жизни не более 8 часов.

**REQ-AUTH-002.** Система ДОЛЖНА возвращать `401` с телом `application/problem+json` при неверной паре
email и пароль, не раскрывая, какое из полей неверно.

**REQ-AUTH-003.** Система ДОЛЖНА ограничивать доступ к эндпоинтам `/admin/*` ролью `ADMIN` и возвращать
`403` для роли `EMPLOYEE`.

### 4.2. Просмотр комнат и слотов (VIEW)

**REQ-VIEW-001.** Система ДОЛЖНА отдавать список только активных комнат с поддержкой фильтров
`capacity_min` (вместимость не меньше указанной) и `q` (подстрока в оборудовании комнаты).

**REQ-VIEW-002.** Система ДОЛЖНА отдавать слоты комнаты на запрошенную дату с шагом 30 минут в интервале
09:00–19:00 Europe/Moscow, помечая каждый слот статусом `free` или `busy`.

**REQ-VIEW-003.** Система ДОЛЖНА хранить и передавать все временные метки в UTC, а отображать и
интерпретировать ввод пользователя в Europe/Moscow.

### 4.3. Бронирование (BOOK)

**REQ-BOOK-001.** Система ДОЛЖНА создавать бронь в статусе `CONFIRMED` без шага согласования и
возвращать `201` с созданным объектом брони.

**REQ-BOOK-002.** Система ДОЛЖНА отклонять создание брони, если её интервал пересекается с интервалом
существующей `CONFIRMED` брони той же комнаты, возвращая `409`.

**REQ-BOOK-003.** Система ДОЛЖНА обеспечивать идемпотентность `POST /bookings` по заголовку
`Idempotency-Key`: повтор с тем же ключом возвращает ранее созданную бронь без создания новой.

**REQ-BOOK-004.** Система ДОЛЖНА разрешать `EMPLOYEE` отменять только собственную бронь и только не
позднее чем за 1 час до её начала; при нарушении возвращать `403` (чужая бронь) или `409` (поздняя отмена).

**REQ-BOOK-005.** Система ДОЛЖНА отдавать сотруднику список его броней с фильтром по статусу и периоду.

**REQ-BOOK-006.** Система ДОЛЖНА валидировать интервал брони: начало кратно 30 минутам, интервал внутри
09:00–19:00 Europe/Moscow, `end_time` строго больше `start_time`; при нарушении возвращать `422`.

### 4.4. Администрирование (ADMIN)

**REQ-ADMIN-001.** Система ДОЛЖНА позволять `ADMIN` создавать комнату с названием, вместимостью и
перечнем оборудования, возвращая `201`.

**REQ-ADMIN-002.** Система ДОЛЖНА позволять `ADMIN` отменять любую бронь в любое время, переводя её
в `CANCELLED`.

**REQ-ADMIN-003.** Система ДОЛЖНА отказывать в создании комнаты с вместимостью меньше 1 или без названия,
возвращая `422`.

### 4.5. Интеграция с внешним календарём (INT)

**REQ-INT-001.** Система ДОЛЖНА публиковать событие создания брони во внешнем календаре асинхронно,
не задерживая ответ на создание брони.

**REQ-INT-002.** Система ДОЛЖНА повторять публикацию при недоступности внешнего календаря не более
3 раз с нарастающей паузой, после чего фиксировать событие в очереди повторов и в журнале.

**REQ-INT-003.** Система ДОЛЖНА публиковать событие отмены брони во внешнем календаре при переходе
брони в `CANCELLED`.

### 4.6. Отчётность (REPORT)

**REQ-REPORT-001.** Система ДОЛЖНА формировать CSV-отчёт по загрузке комнат за период `from`–`to`
(число броней и занятых часов по каждой комнате) и отдавать его с типом `text/csv`.

**REQ-REPORT-002.** Система ДОЛЖНА отклонять запрос отчёта, если `from` больше `to` или период
превышает 366 дней, возвращая `422`.

## 5. Ключевые сценарии использования

### UC-01. Создание брони

| Поле | Значение |
|---|---|
| Акторы | EMPLOYEE (основной), Внешний календарь (второстепенный) |
| Предусловие | пользователь аутентифицирован, комната активна |
| Триггер | сотрудник выбрал свободный слот и нажал «Забронировать» |
| Основной поток | 1) система проверяет интервал (REQ-BOOK-006); 2) проверяет пересечение (REQ-BOOK-002); 3) создаёт бронь `CONFIRMED` (REQ-BOOK-001); 4) асинхронно публикует событие в календарь (REQ-INT-001) |
| Альтернативы | A1: пересечение → `409`; A2: неверный интервал → `422`; A3: календарь недоступен → бронь остаётся `CONFIRMED`, событие уходит в повторы (REQ-INT-002) |
| Постусловие | бронь существует в статусе `CONFIRMED`, слот отображается как `busy` |

### UC-02. Отмена брони

| Поле | Значение |
|---|---|
| Акторы | EMPLOYEE (своя бронь), ADMIN (любая) |
| Предусловие | бронь существует в статусе `CONFIRMED` |
| Триггер | сотрудник или администратор нажал «Отменить» |
| Основной поток | 1) система проверяет право (REQ-BOOK-004); 2) переводит бронь в `CANCELLED`; 3) публикует событие отмены (REQ-INT-003); 4) слот снова `free` |
| Альтернативы | A1: чужая бронь → `403`; A2: менее чем за 1 час → `409`; A3: бронь уже отменена → `409` |
| Постусловие | бронь в `CANCELLED`, слот свободен |

## 6. Логическая модель данных

| Сущность | Ключевые поля | Связи |
|---|---|---|
| `User` | `id` (PK), `email` (UQ), `password_hash`, `role` (`EMPLOYEE`/`ADMIN`), `created_at` | 1:N `Booking` |
| `Room` | `id` (PK), `name`, `capacity`, `equipment` (массив строк), `is_active`, `created_at` | 1:N `Booking` |
| `Booking` | `id` (PK), `user_id` (FK), `room_id` (FK), `start_time` (timestamptz, UTC), `end_time`, `status` (`CONFIRMED`/`CANCELLED`), `idempotency_key` (UQ), `created_at`, `cancelled_at` | N:1 `User`, N:1 `Room` |

Ограничения целостности: `end_time > start_time`; нет двух `CONFIRMED` броней с пересечением по одной
комнате (проверяется транзакционно); `idempotency_key` уникален.

## 7. Требования к API

| Метод и путь | Назначение | Роль | Успех | Ошибки |
|---|---|---|---|---|
| `GET /rooms` | список активных комнат, фильтры `capacity_min`, `q` | любая аутентифицированная | 200 | 401, 500 |
| `GET /rooms/{roomId}/slots?date=` | слоты на дату | любая | 200 | 401, 404, 422 |
| `POST /bookings` | создание брони, `Idempotency-Key` | EMPLOYEE | 201 | 400, 401, 409, 422, 500 |
| `GET /bookings/my` | мои брони | EMPLOYEE | 200 | 401, 500 |
| `PATCH /bookings/{bookingId}/cancel` | отмена | EMPLOYEE, ADMIN | 200 | 401, 403, 404, 409, 500 |
| `POST /admin/rooms` | создание комнаты | ADMIN | 201 | 401, 403, 422, 500 |
| `GET /admin/reports/load?from=&to=` | CSV-отчёт | ADMIN | 200 (`text/csv`) | 401, 403, 422, 500 |

Формат ошибок: `application/problem+json` (RFC 7807) — поля `type`, `title`, `status`, `detail`, `instance`.

## 8. Требования к качеству (сводка)

Полный каталог — `quality/nfr_catalog.md`. Кратко: p95 чтения ≤ 300 мс, p95 создания брони ≤ 500 мс,

в журнале аудита, данные — синтетические.

## 9. Критерии приёмки

| ID | Требование | Given / When / Then |
|---|---|---|
| AC-001 | REQ-AUTH-001 | Given пользователь с валидной парой email/пароль, When он вызывает логин, Then получает JWT со сроком ≤ 8 часов |
| AC-002 | REQ-AUTH-002 | Given неверный пароль, When выполняется логин, Then ответ 401, тело `application/problem+json`, в `detail` нет признака «неверный пароль» или «неизвестный email» |
| AC-003 | REQ-AUTH-003 | Given токен с ролью EMPLOYEE, When запрос к `/admin/rooms`, Then 403 |
| AC-004 | REQ-VIEW-001 | Given 3 активные и 1 неактивная комната, When `GET /rooms`, Then в ответе 3 комнаты без неактивной |
| AC-005 | REQ-VIEW-001 | Given комнаты с вместимостью 4 и 12, When `GET /rooms?capacity_min=10`, Then в ответе только комната на 12 |
| AC-006 | REQ-VIEW-002 | Given дата в рабочие дни, When `GET /rooms/{id}/slots?date=…`, Then 20 слотов по 30 минут с 09:00 до 19:00 Europe/Moscow, у каждого статус `free` или `busy` |
| AC-007 | REQ-VIEW-003 | Given бронь создана на 10:00 МСК, When клиент получает её по API, Then `start_time` в UTC (`07:00Z`), а отображение в UI — 10:00 Europe/Moscow |
| AC-008 | REQ-BOOK-001 | Given свободный слот, When `POST /bookings`, Then 201 и `status=CONFIRMED` |
| AC-009 | REQ-BOOK-002 | Given существующая CONFIRMED бронь 10:00–11:00, When создаётся бронь 10:30–11:30 в той же комнате, Then 409 |
| AC-010 | REQ-BOOK-002 | Given существующая CONFIRMED бронь 10:00–11:00, When создаётся бронь 11:00–12:00, Then 201 (смежные интервалы не считаются пересечением) |
| AC-011 | REQ-BOOK-003 | Given запрос с `Idempotency-Key: K`, When тот же запрос повторён с `K`, Then возвращается та же бронь, вторая не создаётся |
| AC-012 | REQ-BOOK-003 | Given запрос без `Idempotency-Key`, When `POST /bookings`, Then 400 |
| AC-013 | REQ-BOOK-004 | Given сотрудник отменяет свою бронь за 2 часа, When `PATCH …/cancel`, Then 200 и `status=CANCELLED` |
| AC-014 | REQ-BOOK-004 | Given сотрудник отменяет свою бронь за 30 минут, When `PATCH …/cancel`, Then 409 |
| AC-015 | REQ-BOOK-004 | Given сотрудник отменяет чужую бронь, When `PATCH …/cancel`, Then 403 |
| AC-016 | REQ-BOOK-005 | Given у сотрудника 3 брони, When `GET /bookings/my?status=CONFIRMED`, Then в ответе только CONFIRMED |
| AC-017 | REQ-BOOK-006 | Given интервал 10:15–10:45, When `POST /bookings`, Then 422 (начало не кратно 30 минутам) |
| AC-018 | REQ-BOOK-006 | Given интервал 18:30–20:00, When `POST /bookings`, Then 422 (вне рабочих часов) |
| AC-019 | REQ-ADMIN-001 | Given токен ADMIN, When `POST /admin/rooms` с названием и вместимостью, Then 201 и комната доступна в `GET /rooms` |
| AC-020 | REQ-ADMIN-002 | Given бронь сотрудника через 10 минут, When ADMIN отменяет её, Then 200 и `status=CANCELLED` |
| AC-021 | REQ-ADMIN-003 | Given вместимость 0, When `POST /admin/rooms`, Then 422 |
| AC-022 | REQ-INT-001 | Given внешний календарь отвечает 5 секунд, When создаётся бронь, Then ответ 201 приходит быстрее 1 секунды |
| AC-023 | REQ-INT-002 | Given внешний календарь недоступен, When создаётся бронь, Then выполняется не более 3 попыток, событие попадает в очередь повторов, бронь остаётся CONFIRMED |
| AC-024 | REQ-INT-003 | Given CONFIRMED бронь, When она отменена, Then во внешний календарь уходит событие отмены |
| AC-025 | REQ-REPORT-001 | Given период с 5 бронями, When `GET /admin/reports/load`, Then ответ 200, `content-type: text/csv`, в файле строка на каждую комнату с числом броней и занятых часов |
| AC-026 | REQ-REPORT-002 | Given `from` позже `to`, When запрос отчёта, Then 422 |
